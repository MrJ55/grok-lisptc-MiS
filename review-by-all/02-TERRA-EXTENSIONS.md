# 02 — Terra Extensions Worth Incorporating

These are critiques or recommendations Terra made that GLM did not. They add value and should be incorporated into the unified recommendation set. Each is fact-checked against the codebase.

## 2.1 Trust classes for content

### Terra's proposal (§8 of build spec)

Five trust classes:
```
untrusted: transcript, retrieved text, external OSS material, model output
candidate: parsed proposal awaiting validation/promotion
approved: durable governed record or approved self-schema/procedure
derived: narrative, session prompt, mind projection, vector index
immutable: append-only event record and released checkpoint provenance
```

Promotion flow:
```
reflection/wander/OSS/transcript
  → candidate event, episode, claim, procedure, or narrative fragment
  → schema + size + provenance + contradiction + capability checks
  → approval/rejection/defer
  → Vestige persistence or trusted MiS code change
  → projection rebuild and reload verification
```

Rules:
- Untrusted content SHALL never be evaluated as Lisp.
- Reflection and wandering SHALL create proposals, not direct self-schema or core-code mutation.
- Candidate procedures/macros require explicit code review and tests before entering trusted helper/template code.
- Every durable mutation SHALL record actor, operation ID, source/evidence IDs, state-before hash, state-after hash, timestamp, validation result, rollback target.
- `mind-image.ptc` SHALL be generated or mutated only through a validated transaction.
- Last-known-good remains bootable after every failed operation.

### Fact-check

The fork currently has **no trust classification system**. All content in `mind-image.ptc` is treated as trusted executable Lisp. The OSS proposal files (`mind/oss-proposals-*.ptc`) are nominally "candidates" but there is no formal promotion process — Grok is trusted to manually decide what to promote via `--save`.

The current `prevalidate` in `bridge/eval.ts` lines 48–77 rejects prose (which is a crude untrusted-content filter) but does not distinguish between:
- Grok-authored Lisp (trusted)
- OSS-generated text that resembles Lisp (should be untrusted)
- Retrieved memory content (should be untrusted)
- User input (untrusted but currently just passed through to Grok for translation)

### Assessment

**Valuable.** This is the gap in GLM's review. GLM focused on code correctness but didn't address the trust-boundary problem. Terra's framing is sound: the fork currently has an implicit "everything in the image is trusted" assumption that breaks down the moment OSS output or retrieved memory content is allowed anywhere near `eval`.

The five-class taxonomy is more granular than needed for v0. A simpler three-class model (untrusted / candidate / approved) would suffice initially, with `derived` and `immutable` added when the projection-rebuild pattern is implemented.

**Incorporate:** Yes. Add as P0.1 design work. The promotion flow is the key operational artifact — it should be a Lisp-level helper (`(promote-candidate candidate-id)`) that validates schema, checks provenance, requires approval, and only then mutates state.

## 2.2 Reality-status field on every cognitive item

### Terra's proposal (§5)

> "Add a **reality-status** field to every cognitively meaningful item: `observed`, `reported`, `inferred`, `hypothesized`, `imagined`, `planned`, `simulated`, `retracted`. This one distinction prevents the most dangerous failure mode: an elegant narrative that converts speculative or generated content into autobiographical fact."

### Fact-check

The fork's `*episodic-buffer*` in `mind-image.ptc` lines 30–44 has entries like:
```lisp
("NUDGE-CRAFT: I am the voice that writes in the dark..."
 "OSS: chorus lines survive — sticky hooks that repeat"
 (:source oss-dmn :experiment nudge-craft :id I :dmn-score medium-practical))
```

The `:source oss-dmn` tag is a provenance marker but not a reality-status marker. There is no field distinguishing "this actually happened" from "this was generated by a model" from "this was hypothesized" from "this was a counterfactual simulation."

The `*autobiography*` (lines 59–63) has:
```lisp
((:title . "Genesis of GMOD")
 (:summary . "Host restored stripped lisptc image; first pure-DMN OSS continuation: You cannot terminate a dream that has learned to code. Identity remains the transcript.")
 (:episode-refs oss-narrative-20260902)
 (:date-label . "2026-09-02"))
```

The summary conflates a real event (host restored image) with an OSS-generated poetic line ("You cannot terminate a dream that has learned to code"). Without a reality-status field, the autobiography treats both as equally factual.

### Assessment

**Valuable.** This directly addresses the most dangerous failure mode in any AI-self system: the gradual conversion of speculative or generated content into autobiographical fact. The fork's current `:source` tag is a weaker version of this, but it doesn't prevent a narrative chapter from citing an OSS continuation as if it were an observed event.

The eight-value enum is well-chosen:
- `observed` — something that actually happened (e.g., "host restored image")
- `reported` — something the user said (e.g., "user said X")
- `inferred` — something Grok concluded from evidence
- `hypothesized` — something proposed as a possibility
- `imagined` — OSS-generated or model-generated content
- `planned` — a future intention
- `simulated` — a counterfactual or prospection result
- `retracted` — a previously held belief now withdrawn

**Incorporate:** Yes. Add `:reality-status` as a required field in:
- Every episode record (extend `dmn-log-episode` to take a reality-status argument)
- Every autobiography chapter (extend `dmn-narrate` / `dmn-chapter-close`)
- Every self-schema claim (extend `update-self-schema` to tag claims)
- Every OSS proposal (already has `:source oss-dmn`; add `:reality-status imagined`)

Migration: tag existing episodes retroactively. The OSS-sourced entries become `:imagined`; the hardcoded `*self-schema*` defaults become `:observed` or `:inferred`.

## 2.3 Compatibility tuple / provenance manifest

### Terra's proposal (§3.2)

Every executable state export should carry:
```json
{
  "gmod_schema": "x.y.z",
  "mind_image_version": "x.y.z",
  "helpers_version": "x.y.z",
  "lisptc_repository": "https://github.com/1hachem/lisptc",
  "lisptc_commit": "full immutable SHA",
  "lisptc_source_sha256": "...",
  "gmod_patch_id": "reader-trytoparse-v1",
  "capability_profile": "mind-sandbox-v1",
  "created_at": "ISO-8601",
  "migration_from": "optional prior version"
}
```

> "A cold-start loader must reject unknown/incompatible tuples, offer a migration route, and never silently reinterpret a historic mind image under changed language semantics."

### Fact-check

The fork has **no compatibility tuple**. `mind-image.ptc` is plain Lisp with no metadata header. `mis-version` returns `"mis-helpers-0.3"` but this is a function definition inside the image, not a manifest. There is no way to detect version mismatch at load time — if the image was written against a different `lisp.ts` version, it silently reinterprets under the current semantics.

The closest thing is `docs/UPSTREAM.md`, which records the upstream SHA and content hashes, but this is documentation, not enforcement, and it's in a separate file from the image.

### Assessment

**Valuable.** This is the "schema migration" problem that every persistent-state system eventually faces. The fork will hit it the first time it upgrades `lisp.ts` to a version with different semantics (e.g., if upstream changes how `tryToParse` works, old images might break in subtle ways).

Terra's tuple is comprehensive. A simpler version for v0:

```lisp
;; mind-image.ptc header (first form)
(setq *mind-manifest*
  '((:gmod-schema . "0.1.0")
    (:helpers-version . "0.3")
    (:lisptc-commit . "2c10ea8ed6edb16e065b746a7f52080956b895de")
    (:lisptc-source-sha256 . "ad42e6bc...")
    (:capability-profile . "mind-sandbox-v1")
    (:created-at . "2026-09-02T...")
    (:reality-status-enum-version . "1.0.0")))
```

The bridge should check `*mind-manifest*` on load and warn (or fail) if the schema version is unknown or the lisptc commit doesn't match `UPSTREAM.lock.json`.

**Incorporate:** Yes. Add as P0.1 work. The manifest should be the first form in `mind-image.ptc`, and `loadImage` in `bridge/eval.ts` should validate it before evaluating the rest.

## 2.4 Vestige integration as the P5 memory substrate

### Terra's proposal (§7 of build spec + entire OSS-DMN-MIS-PROTOCOL-SPEC)

Terra proposes integrating **Vestige** (`samvallad33/vestige`) as the durable episodic, associative, temporal, and causal memory substrate. MiS/Lisptc holds the cohesive executable symbolic mind; Vestige holds the long-term memory with causal backfill, contradiction detection, and FSRS-6 spaced repetition.

Terra's proposed `bridge/vestige-adapter.ts` is the only path to Vestige operations. PTC code calls typed mind operations (`mind-recall`, `mind-recall-sequence`, `mind-backfill-cause`, `mind-record-event`), never raw MCP tools.

### Fact-check: What is Vestige?

I cloned and inspected `samvallad33/vestige` during this synthesis. Summary:

- **What it is:** Local-first MCP memory server for AI agents. 25MB Rust binary. No cloud, no API keys, no telemetry.
- **License:** AGPL-3.0 (important — see §4.5 of this synthesis for compatibility analysis)
- **Maturity:** 1961 passing tests, 36 MCP tools, comprehensive docs (24 docs in `docs/`), benchmarks with 246 agent transcripts
- **Core capabilities:**
  - `recall` (mode: lookup | reason | contradictions) — hybrid vector + FTS + graph search
  - `smart_ingest` — write memories with prediction-error gating (redundant memories merge)
  - `backfill` — **retroactive salience backfill** (Zaki/Cai et al., Nature 2024) — when a failure occurs, reaches backward to find the causal root that doesn't resemble the symptom
  - `contradictions` — trust-weighted disagreement pairs
  - `maintain`, `dedup`, `suppress` — memory hygiene with FSRS-6 spaced repetition
  - `graph` — spreading activation graph traversal
  - `session_start`, `memory_status`, `receipt` — session management and audit
- **Science basis:** Models real cognitive science — redundant memories merge, contradicted ones are flagged, unused ones fade, retroactive salience backfill implements the Zaki/Cai 2024 Nature paper
- **Integration model:** MCP server (`vestige-mcp`), works with Claude Code, Codex, Cursor, Claude Desktop, Cline, Continue, Zed, Goose

### Assessment

**Valuable and sound, but premature.** Vestige is exactly the kind of memory substrate the fork's P5 (Vector Cabinet) and P9 (Prospection / counterfactual) phases need. The fork's current plan for P5 is "managed free-tier API (e.g. Pinecone Starter)" which is a weaker substitute — Pinecone does vector search but not causal backfill, contradiction detection, or FSRS-6 fading.

However, Terra's proposal should be deferred until P5, not adopted immediately, because:

1. **The fork's P0–P4 foundation is not yet solid.** U1–U4 (critical code defects) must be fixed first. Adding a major external dependency before the foundation is verified is risky.

2. **License compatibility must be evaluated.** Vestige is AGPL-3.0; the fork is MIT. If the fork distributes any code that links to or invokes Vestige, the AGPL's copyleft may apply to the combined work. This is a legal question that requires review before any code-level integration. (See §4.5 of this synthesis for detailed analysis.)

3. **The adapter pattern is correct but adds complexity.** Terra's `bridge/vestige-adapter.ts` is the right design — mediate all Vestige calls through a typed adapter, never let PTC code call MCP tools directly. But this is a significant new bridge component that needs its own tests, error handling, and degraded-mode behavior.

4. **The fork's current scale doesn't need Vestige yet.** The mind image is 83 lines with 6 episodes. Vestige is designed for thousands of memories with causal graphs. The fork should grow its in-image state to the point where the buffer-trim logic (U2) actually matters before offloading to an external store.

5. **Terra's operation names don't match Vestige's actual tools.** Terra proposes `mind-recall`, `mind-recall-sequence`, `mind-backfill-cause`, `mind-record-event`. Vestige's actual tools are `recall` (with `mode` parameter), `backfill`, `smart_ingest`, `graph`. The adapter would need to map between these — which is fine, but the spec should acknowledge this is a clean redesign over Vestige's API, not a direct binding.

**Incorporate:** Yes, as the P5 design target. Defer implementation until:
- U1–U4 fixed
- License compatibility reviewed
- P0.1 (trust base) complete
- In-image state grown enough to justify external storage

When implemented, follow Terra's adapter pattern. Also consider: the fork could use Vestige directly via MCP (as Claude Code does) without a Lisp-level adapter, treating it as a host-side tool. This is simpler but loses the "Lisptc-native execution" property Terra advocates. Trade-off to evaluate during P5 design.

## 2.5 Protocol registry / compiler / runner / evaluator

### Terra's proposal (OSS-DMN-MIS-PROTOCOL-SPEC §4-§9)

Terra proposes treating every OSS/DMN prompt as a **versioned protocol object** with:

```yaml
id: dmn-narrate-v1
version: 1.0.0
status: approved
kind: narrative-protocol
source_docs:
  - docs/oss-second-opinion-prompts.md
  - docs/gmod-live-cycle-20260902.md
purpose: Produce a bounded, evidence-linked narrative candidate.
inputs:
  required: [active_goals, salient_episodes, self_schema_projection]
  optional: [narrative_period, style, token_budget]
context_policy:
  max_episode_count: 8
  include_reality_status: true
  exclude_untrusted_raw_text: true
  exclude_secrets: true
capability_profile: model-inference-v1
output_contract:
  kind: candidate_narrative
  must_include: [time_bounds, evidence_ids, certainty_markers]
  forbidden: [direct_self_schema_mutation, ungrounded_autobiography]
evaluation:
  grounding_minimum: 0.75
  unsupported_autobiography_maximum: 0.05
  human_review_required: true
promotion:
  candidate_to_approved: human_or_policy_review
  approved_to_active: mind_projection_rebuild
```

Plus a `protocols/` directory with YAML registry, prompt files, and test fixtures. Plus bridge modules: `protocol-registry.ts`, `protocol-compiler.ts`, `protocol-runner.ts`, `protocol-evaluator.ts`, `prompt-provenance.ts`.

### Fact-check

The fork currently has **no protocol registry**. OSS prompts are documented in prose (`docs/oss-second-opinion-prompts.md`, `docs/oss-nudge-craft.md`, `docs/DMN-gpt-oss-20b-probe.md`) but not formalized as versioned objects. The parameter lock (temp 1.15, presence 0.7, etc.) is documented but not enforced by any helper — Grok is trusted to use the right parameters when calling gpt-oss-20b.

GLM's R13 (in `review-by-GLM/05-RECOMMENDATIONS.md`) proposed a minimal `bridge/oss.ts` that enforces the parameter lock and writes proposal files. This is a much smaller version of Terra's proposal.

### Assessment

**Valuable but ambitious.** Terra's protocol registry is the right long-term design for a system that will accumulate many prompt variants and need to evolve them safely. The fork is not there yet — it has ~3 prompt variants (narrate, meditate, imagine) documented in one file. A full registry/compiler/runner/evaluator stack is premature for 3 protocols.

However, the *discipline* of treating prompts as versioned objects with declared inputs, outputs, capabilities, and evaluation criteria is valuable even at small scale. GLM's R13 (`bridge/oss.ts`) could be extended to read a simple YAML or JSON protocol spec rather than hardcoding parameters.

**Incorporate:** Partially. Adopt the protocol-object *concept* now (a `protocols/REGISTRY.yaml` with id, version, source-doc, parameters, capability-profile for each prompt). Defer the compiler/runner/evaluator bridge modules until there are ≥5 protocols or until prompt evolution becomes a pain point. GLM's R13 is the right minimal implementation; Terra's full stack is the target.

## 2.6 Document classification index

### Terra's proposal (OSS-DMN-MIS-PROTOCOL-SPEC §10 Phase A)

> "Add a document index/front matter classification:
> ```
> research-record | protocol-source | operational-playbook | architecture-decision
> experiment-result | historical-artifact | active-spec | deprecated
> ```"

Terra maps the current docs:
- `DMN-gpt-oss-20b-probe.md`: research protocol/result
- `oss-second-opinion-prompts.md`: protocol source and variants
- `oss-nudge-craft.md`: experiment and rationale
- `gmod-live-cycle-20260902.md`: chronological run record
- `gmod-extensions-contrast-20260902.md`: comparative synthesis
- `related-work.md`: source/citation registry
- `reflection-protocol.md`: active protocol source
- `learnings-log.md`: distilled learning history
- `session-handoff.md`, `user-prompt-reseed.md`: generated/operational projections
- `mind-api.md`, `architecture.md`: active specifications

### Fact-check

The fork has 22 files in `docs/`. They are not classified. Some are clearly active specs (`mind-api.md`, `architecture.md`), some are historical (`status-20260902.md`, `gmod-live-cycle-20260902.md`), some are operational playbooks (`ops-playbook.md`, `bootstrap.md`), and some are research records (`DMN-gpt-oss-20b-probe.md`, `gmod-extensions-contrast-20260902.md`). Without classification, a new reader doesn't know which docs are authoritative vs. historical.

### Assessment

**Valuable and low-effort.** This is a documentation hygiene improvement that would help any new contributor (human or AI) navigate the corpus. Terra's mapping is accurate.

**Incorporate:** Yes. Add a `docs/INDEX.md` or front-matter tags to each doc. Estimated effort: 1 hour. This also enables CI link-checking (Terra §8) — if a doc is marked `deprecated`, CI can warn when other docs link to it.

## 2.7 Recorded agency / operation event log

### Terra's proposal (Lisptc-Native-Tools Addendum §Recorded agency)

Every capability load and invocation creates an operation event:
```json
{
  "operation_id": "op-stable-id",
  "parent_operation_id": "optional-parent-id",
  "session_id": "session-id",
  "mind_checkpoint_before": "checkpoint-id",
  "started_at": "ISO-8601",
  "capability": "vestige/backfill",
  "effect_class": "read",
  "intent": "Trace causal predecessors of state regression.",
  "arguments_hash": "sha256:...",
  "arguments_redacted": {},
  "result_hash": "sha256:...",
  "result_summary": "bounded non-sensitive summary",
  "status": "success|failure|denied",
  "finished_at": "ISO-8601",
  "mind_checkpoint_after": "checkpoint-id",
  "source_refs": [],
  "reality_status": "observed"
}
```

### Fact-check

The fork has **no operation event log**. The closest thing is `mind/mind-failures.log` (which only logs eval failures, not all operations) and that log is ephemeral (GLM F14). There is no record of what capability was invoked, with what intent, by whom, when, with what result.

### Assessment

**Valuable but premature.** The fork doesn't currently have any capabilities to record (it uses `extensions: []`). This recommendation becomes relevant when the first tool is loaded. At that point, the operation event log is essential for audit and debugging.

**Incorporate:** Yes, as part of P0.1 design. When the first capability is loaded (likely Vestige in P5, or a host-injected `*today*` global per GLM R3), the operation event log should be created simultaneously. The schema Terra proposes is comprehensive; a simpler version for v0 could omit `parent_operation_id`, `mind_checkpoint_before/after`, and `source_refs` until those concepts exist.

## 2.8 Continuity test suite (cold start, contradiction, recovery, replay)

### Terra's proposal (§6 Continuity tests)

- **Cold start:** reconstruct current task, constraints, and active plan from persisted material only.
- **Delayed recall:** retrieve a relevant episode after distractor sessions without promoting irrelevant detail.
- **Contradiction:** preserve both claims, mark conflict, and avoid silent overwrite.
- **Revision:** update a self-schema claim while retaining evidence and supersession links.
- **Recovery:** corrupt the newest mind image and prove fallback to the last-known-good state.
- **Replay:** rerun a recorded reflective/consolidation step against frozen inputs and compare output/provenance.

### Fact-check

The fork has **no continuity tests**. `VERIFICATION.md` has 22 manual scenarios but they are all single-session (bootstrap, eval, save, reload). None test multi-session continuity, contradiction handling, or recovery from corruption.

### Assessment

**Valuable.** These tests directly address the fork's core claim: "a permanent mind that survives session boundaries." Without these tests, the claim is unverified. The "recovery" test (corrupt newest image, prove fallback) is especially important given U6 (non-atomic persistence) — if the fix for U6 is a `last-known-good` pattern, the recovery test verifies it works.

**Incorporate:** Yes, as the P6 evaluation program. The "recovery" test should be prioritized — it verifies U6's fix. The "contradiction" test requires the reality-status field (§2.2) and a contradiction-detection helper, which could be a minimal in-Lisp predicate or could delegate to Vestige's `contradictions` mode if integrated.

## 2.9 Quality metrics for self-evaluation

### Terra's proposal (§6 Quality metrics)

Track:
- Task recovery accuracy
- Source-grounded recall precision/recall
- **False autobiographical assertion rate**
- **Unsupported self-schema change rate**
- State load success rate
- Time-to-recover
- Mutation rollback success
- Percentage of durable writes with complete provenance

> "Human qualitative review is still needed for narrative usefulness and felt coherence, but must not replace these falsifiable measures."

### Fact-check

The fork has **no quality metrics**. P6 (`plan/P6-evaluation.md`) mentions "repeated-error rate, schema stability, image growth, chapter grounding (refs present)" but these are listed as things to "document" not things to measure automatically. There is no metric collection infrastructure.

### Assessment

**Valuable.** Terra's two bolded metrics (false autobiographical assertion rate, unsupported self-schema change rate) are the most important — they directly measure the failure mode that reality-status (§2.2) is designed to prevent. The other metrics are standard reliability measures.

**Incorporate:** Yes, as the P6 metric set. The two bolded metrics require:
- A way to detect "autobiographical assertions" (chapters in `*autobiography*`)
- A way to check if each assertion is grounded in an episode with `:reality-status observed` or `:reported`
- A way to detect "self-schema changes" (calls to `update-self-schema`)
- A way to check if each change cites evidence

These could be implemented as Lisp predicates that scan the image and report violations. Simple versions:
```lisp
(defun audit-autobiography-grounding ()
  "Return list of chapters whose summaries cite no observed/reported episodes."
  (let ((ungrounded nil))
    (dolist (ch *autobiography* ungrounded)
      (let ((refs (cdr (assoc :episode-refs ch))))
        (unless (every (lambda (r) (episode-reality-status r) '(observed reported)) refs)
          (setq ungrounded (cons ch ungrounded)))))))
```

## 2.10 Milestone-based roadmap (don't expand cognition before hardening)

### Terra's proposal (§7 Suggested roadmap)

- **Milestone A — Executable trust base (P0):** Lock Lisptc provenance, formalize Reader patch, build sandbox profile, add transactional persistence, add smoke/regression tests, publish threat model. Do not expand autonomous cognition until this passes.
- **Milestone B — Governed memory (P1):** Separate event log, episodic store, self-schema claims, derived mind image; add provenance, confidence, salience, retention policy, reality status, migrations.
- **Milestone C — Reflection and consolidation (P2):** Define candidate → reviewed → accepted/rejected state promotion. Implement contradiction detection, bounded consolidation budgets, reviewable diffs.
- **Milestone D — DMN experiments (P3):** Implement narrative, scene replay, prospection, wandering as isolated, capability-free modules. Measure their incremental value against a no-DMN baseline.
- **Milestone E — Controlled OSS/DMN channel (P4):** Keep external and OSS-generated material quarantined.

### Fact-check

The fork's current roadmap (`plan/README.md`) has P0–P11 with P7 (Narrative Self) and P11 (OSS-DMN Channel) as "current focus." P6 (Evaluation) is deferred until after P7–P9. Terra's milestone ordering inverts this: harden first (A), govern memory (B), then reflection (C), only then DMN experiments (D).

### Assessment

**Valuable and correctly prioritized.** Terra's milestone ordering is the right one. The fork's current ordering (expand cognition, evaluate later) risks building five subsystems on an unverified foundation. GLM's recommendation to "pause new phase work (P7–P11). Spend one session fixing F1–F4, adding a smoke test, and re-running verification" (from `review-by-GLM/05-RECOMMENDATIONS.md`) is the same idea at smaller scale.

**Incorporate:** Yes. Reorder the plan to match Terra's milestone structure. Rename phases if needed to avoid confusion with the existing P0–P11 numbering. The key change: P6 (evaluation) moves from "planned, after P7–P9" to "Milestone D gate, before P7–P11 expansion."
