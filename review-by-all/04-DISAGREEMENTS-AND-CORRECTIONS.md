## 4.1 Disagreement: Is the Reader patch necessary or unnecessary?

### Terra's position

Terra treats the Reader `tryToParse` patch as a necessary evil to be formalized:
> "Replace any bootstrap search-and-rewrite operation with a tracked unified patch: `patches/lisptc-reader-trytoparse.patch`."
> "Record why the Reader patch exists, the smallest failing input, expected output, upstream issue/PR status, and removal criteria."

Terra recommends keeping the patch but making it tracked, versioned, and removable when upstream fixes the bug.

### GLM's position

GLM identifies that the patch is unnecessary because the fork caused the bug by rewriting `arith.ts`:
> "The fork's `src/arith.ts` was silently rewritten to return `undefined` from `tryToParse` (upstream returns `null`). The 'Reader fix' is patching a self-inflicted wound. Reverting to upstream `arith.ts` eliminates the need for the patch entirely."

GLM recommends reverting `arith.ts` to upstream verbatim and deleting the patch.

### Evidence

**Upstream `arith.ts` (commit `2c10ea8`, the fork's claimed pin):**
```typescript
export function tryToParse(token: string): Numeric | null {
    try {
        return BigInt(token);
    } catch (_ex) {
        const n = Number(token);
        if (Number.isNaN(n)) return null;
        return n;
    }
}
```
Returns `null` on failure.

**Fork's `src/arith.ts`:**
```typescript
export function tryToParse(s: string): Numeric | undefined {
    if (/^[+-]?\d+$/.test(s)) return BigInt(s);
    const n = Number(s);
    if (!Number.isNaN(n)) return n;
    return undefined;
}
```
Returns `undefined` on failure.

**Upstream `lisp.ts` reader (all commits):**
```typescript
const n = tryToParse(t);
if (n !== null) this.token = n;
```

With upstream `arith.ts`: `n === null` → `n !== null` is false → token NOT set → falls through to symbol/keyword handling. **Correct.**

With fork `arith.ts`: `n === undefined` → `n !== null` is true (undefined !== null) → `this.token = undefined` → list parsing breaks. **Bug.**

### Resolution

**GLM is correct.** The patch is unnecessary. The bug only exists because the fork rewrote `arith.ts`. If the fork uses upstream `arith.ts` verbatim, the reader works correctly without any patch.

Terra's recommendation to formalize the patch is not wrong — it's a good practice for any *necessary* patches. But this patch is not necessary; it's a workaround for a self-inflicted divergence. The right action is to eliminate the divergence, not to formalize the workaround.

**Unified recommendation:** Revert `src/arith.ts` to upstream (GLM R4). Delete the `sed` patch in `bootstrap.sh`. Delete `src/READER-FIX.md`. Then adopt Terra's `UPSTREAM.lock.json` + `patches/` discipline for any future *genuinely necessary* patches.

## 4.2 Disagreement: Should `mind-image.ptc` be split via `import`?

### Terra's position

Terra recommends a deeper separation: `mind-image.ptc` should be a "versioned executable projection assembled from governed state" — i.e., generated, not directly edited. The governed state lives in separate stores (event log, episodic store, self-schema, narrative). Terra's proposed layout includes `mind/mind-image.template.ptc` (template), `mind/projections/current-context.ptc` (generated), `mind/policies/mutation-rules.ptc` (policy).

### GLM's position

GLM recommends a simpler split using upstream's `(import "path")`:
```
mind/
  mind-image.ptc          ;; loader: (import "helpers.ptc") (import "schema.ptc") ...
  helpers.ptc
  schema.ptc
  episodes.ptc
  autobiography.ptc
  arithmetic.ptc
```

The loader is a thin sequence of imports. Each file is directly editable.

### Resolution

**Both are right at different scales.** GLM's `import`-based split is the right v0.1 step — it's a file reorganization that preserves the current "directly editable" property while making the structure clearer. Terra's "generated projection" model is the right long-term target — it separates governed state from executable projection, which is necessary for trust-class enforcement (§2.1).

**Unified recommendation:**
1. **Short term (P0.1):** Apply GLM's `import`-based split. This is a 1-hour change that immediately helps.
2. **Long term (P0.2+):** Adopt Terra's "generated projection" model. The `mind-image.ptc` becomes a build artifact generated by `scripts/build-mind-image.ts` from governed state in `state/`. Direct editing of the image is replaced by editing the governed state and rebuilding.

## 4.5 Factual issue: Terra's build spec uses `(load ...)` which is not an upstream builtin

### Terra's claim

`review-by-Terra/GMOD-MIND-VESTIGE-BUILD-SPEC-2026-09-02.md` line 92–94:
```lisp
(load "mind/helpers.ptc")
(load "mind/projections/current-context.ptc")
```

### Fact-check

```
$ cd lisptc-upstream && grep -n '"load"\|(load\|(defun load' packages/interpreter/src/lisp.ts
(no matches for "load" as a builtin)

$ grep -n '"import"' packages/interpreter/src/lisp.ts
958:			"import",
```

Upstream lisptc has `(import "path")` as a builtin (line 958, with full implementation at the `def` call). There is no `load` builtin. Terra's proposed Lisp code would fail with `unbound variable load`.

### Impact

Low — this is in a proposed spec, not in running code. But anyone trying to implement Terra's build spec would hit this immediately.

### Correction

Replace `(load "mind/helpers.ptc")` with `(import "mind/helpers.ptc")` throughout Terra's build spec. Note that `import` resolves relative paths against the importing file's directory, so if `mind-image.ptc` is in `mind/`, the import should be `(import "helpers.ptc")` (relative), not `(import "mind/helpers.ptc")` (absolute from cwd).

## 4.6 Factual issue: Terra's "Vestige" was initially misread by GLM as invented

### Context

In my (GLM's) original audit (`review-by-GLM/`), I noted that "Vestige" appears in the fork's own docs as a common noun meaning "trace/remnant" and concluded that Terra's "Vestige" subsystem was a greenfield proposal not grounded in the fork. The user corrected this: Vestige refers to `https://github.com/samvallad33/vestige/tree/main`, an external project.

### Fact-check after correction

I cloned and inspected `samvallad33/vestige`:
- **Real project:** 25MB Rust binary, local-first MCP memory server
- **License:** AGPL-3.0
- **Maturity:** 1961 passing tests, 36 MCP tools
- **Capabilities:** `recall`, `smart_ingest`, `backfill` (retroactive salience), `contradictions`, `maintain`, `dedup`, `graph`, `session_start`, `memory_status`, `receipt`, etc.
- **Science basis:** Zaki/Cai et al. Nature 2024 (retroactive salience backfill), FSRS-6 spaced repetition, prediction-error gating

### Assessment

Terra's recommendation to integrate Vestige is sound and well-grounded. Vestige directly addresses the fork's P5 (Vector Cabinet) and P9 (Prospection / counterfactual) needs with a mature, tested, local-first implementation. The fork's current P5 plan ("managed free-tier API like Pinecone") is a weaker substitute — Pinecone does vector search but not causal backfill, contradiction detection, or FSRS-6 fading.

### License compatibility analysis

**Vestige license:** GNU Affero General Public License v3.0 (AGPL-3.0)
**Fork license:** MIT (per `LICENSE` file and `README.md` line 70)

AGPL-3.0 is a strong copyleft license. Key considerations:

1. **MCP integration (network call to `vestige-mcp` subprocess):** If the fork communicates with Vestige via MCP (as a separate process, over stdio), this is likely **not** a derivative work. The fork's MIT code and Vestige's AGPL code are separate programs communicating via a protocol. The fork can remain MIT. (This is analogous to a MIT-licensed app calling a GPL-licensed command-line tool via subprocess.)

2. **Direct code linking (Rust FFI or TypeScript import):** If the fork imports Vestige code directly (e.g., `import * from 'vestige-core'`), the AGPL's copyleft would likely apply to the combined work, requiring the fork to become AGPL. This is probably not what the fork wants.

3. **Adapter pattern (Terra's proposal):** Terra's `bridge/vestige-adapter.ts` that calls Vestige via MCP (subprocess) is the safe integration model. The adapter is MIT; Vestige is AGPL; they communicate via MCP protocol. No license contamination.

### Correction

GLM's original review should have noted: "Terra's Vestige proposal references an external project (`samvallad33/vestige`) that I did not inspect. The integration recommendation should be evaluated against Vestige's actual API and license." GLM's original review treated "Vestige" as a Terra invention, which was incorrect.

This synthesis corrects that: Vestige is a real, mature project. Terra's recommendation is well-grounded. The integration should go through MCP (subprocess) to preserve license separation, per Terra's adapter pattern.

## 4.7 Factual issue: Terra's proposed operation names don't match Vestige's actual tools

### Terra's proposed API

```lisp
(mind-recall *mind* :query query :k 5 :mode 'associative)
(mind-recall-sequence *mind* :from event-a :to event-b)
(mind-backfill-cause *mind* :symptom text)
(mind-record-event *mind* event)
```

### Vestige's actual MCP tools

| Terra's name | Vestige's actual tool | Notes |
|---|---|---|
| `mind-recall` | `recall` (mode: lookup \| reason \| contradictions) | Similar; Terra's `:mode 'associative` maps to Vestige's `mode: 'lookup'` |
| `mind-recall-sequence` | `recall` with temporal parameters, or `graph` | No direct equivalent; Vestige's `graph` does spreading activation, not sequence retrieval |
| `mind-backfill-cause` | `backfill` | Direct match (retroactive salience backfill) |
| `mind-record-event` | `smart_ingest` | Similar; Vestige's `smart_ingest` has prediction-error gating and dedup |
| (no equivalent) | `contradictions` (now `recall` mode) | Terra mentions contradiction checking but doesn't propose a specific function |
| (no equivalent) | `maintain`, `dedup`, `suppress` | Vestige's memory hygiene tools; Terra mentions these in the adapter table but doesn't propose Lisp-level names |

### Assessment

Terra's API is a clean redesign, not a direct binding to Vestige. This is fine — the adapter pattern exists precisely to translate between the mind's Lisp-level operations and Vestige's MCP tools. But the spec should acknowledge this mapping explicitly, so implementers know which Vestige tool each operation calls.

### Correction

Terra's build spec should include a mapping table (like the one above) showing how each Lisp-level operation translates to Vestige MCP tool calls. The adapter (`bridge/vestige-adapter.ts`) implements this mapping.

## 4.8 Disagreement: Should the fork adopt Terra's full milestone reordering immediately?

### Terra's position

Terra proposes a complete roadmap reordering (§7):
- Milestone A (P0): harden trust base — pin, patch, sandbox, transactional persistence, tests, threat model
- Milestone B (P1): governed memory — separate event log, episodic store, self-schema, derived mind image
- Milestone C (P2): reflection and consolidation — candidate → reviewed → accepted/rejected
- Milestone D (P3): DMN experiments — measure value against no-DMN baseline
- Milestone E (P4): controlled OSS/DMN channel — quarantine external material

"Do not expand autonomous cognition until this passes."

### GLM's position

GLM recommends a smaller version: "Pause new phase work (P7–P11). Spend one session fixing F1–F4, adding a smoke test, and re-running verification. Then resume P7 with confidence."

GLM doesn't propose a full reordering; it proposes a pause + fix sprint, then resume the existing plan.

### Resolution

**Terra is more ambitious; GLM is more pragmatic.** Both agree the current plan is misordered (expanding cognition before hardening). The question is how much reordering to do.

Terra's full milestone reordering is the right long-term structure, but it requires relabeling all phases (P0–P11 → Milestones A–E), which is disruptive. GLM's "pause and fix" is less disruptive but doesn't address the structural problem that P6 (evaluation) is deferred.

**Unified recommendation:**
1. **Immediate (1 session):** GLM's pause + fix sprint. Fix U1–U4, add smoke test, re-verify. This is non-disruptive and addresses the most critical defects.
2. **Short term (P0.1):** Adopt Terra's Milestone A as a new phase "P0.1 State Governance and Runtime Trust." This is the hardening work (transactional persistence, trust classes, capability profiles, manifest). Don't relabel existing phases.
3. **Medium term (P6 elevation):** Move P6 (Evaluation) to immediately after P0.1, before P7–P11 expansion. This is the key structural change: evaluate before expanding.
4. **Long term (Milestone B–E):** Adopt Terra's milestone structure as the organizing principle for P5–P11, but keep the existing phase numbers for continuity.

This preserves the existing vocabulary while adopting Terra's prioritization.
